# PROTECTION — 方法论保护章节（生长的护栏）

> **版本**：v1.2
> **日期**：2026-09-06
> **性质**：phyt-DNA 方法论组成部分。所有采用本方法论的项目以此为保护规范。
> **哲学立场**：保护是**生长的护栏，不是围墙**。护栏让植物不被踩踏（专利抢注、
> 商标冒用），围墙则隔绝阳光与养分（采用率、社区贡献）——本方法论只要护栏。

## 一、大厂实践提炼（Google / Apple，公开可验证）

### Google——开放标准 + 分层专有

| 实践 | 内容 | 对本方法论的启示 |
|---|---|---|
| 分层策略 | 基础层开放（Android/AOSP、K8s、WebM/AV1），上层专有（搜索/广告） | **协议与规范必须公开**，商业增值层才谈闭源；"开放标准 + 专有服务"是正循环 |
| Apache 2.0 专利授权 | 用 Google 代码即获其内嵌专利授权；独立实现不受保护（Transformer 专利案例） | Apache 2.0 的专利授权是**条件性**的——代码必须真实开源分发才有意义 |
| OPN Pledge | Open Patent Non-Assertion：承诺对特定专利不起诉开源使用者（除非先被攻击） | 防御性承诺有**终止条款**（先被攻击即可收回）——可用作生态信任信号 |
| PAX 交叉授权 | Android 生态企业间免费专利交叉授权（2017） | 生态做大后才相关；个人阶段不启动 |
| 防御性公开 | Google Prior Art 数据库 / Technical Disclosure Commons，专门发布先有技术 | **防御性公开是零成本护城河**——先公开，别人就抢注不了 |
| 标准贡献 | 把技术推成标准（PWA/WebM），标准即免专利攻击面 | 协议设计期就考虑"可标准化"，是终极防御 |

### Apple——混合模式 + 商标护城河

| 实践 | 内容 | 对本方法论的启示 |
|---|---|---|
| 混合模式 | 底层开放（Darwin/WebKit/Swift/LLVM/CUPS），上层闭源（iOS GUI/iMessage） | 与 Google 同构：**基础设施开放，体验/服务专有** |
| Swift：Apache 2.0 + Runtime Exception | 代码 Apache 2.0，运行时库豁免条款便于集成 | 需要"放开集成"时，可加例外条款（按需，非默认） |
| WebKit：BSD + LGPL 混合 | 按组件选许可 | 许可不是一刀切；**按组件特性选许可**（当前生态统一 Apache 2.0 已足够，将来分叉再评估） |
| 商标保护 | "Swift" 是 Apple 注册商标——代码开源但名字受控 | **名字是资产**。项目名/协议名尽早确定并保持（不抢注别人商标，也不让名字裸奔） |
| 贡献者审查 | 严格 code review + 贡献门槛 | 个人项目阶段：CONTRIBUTING.md 声明"贡献者确认不侵犯第三方 IP"即可（零成本） |
| 安全披露 | 负责任披露流程 + 漏洞赏金 | SECURITY.md + 邮箱声明（零成本，按需启用） |

### 跨大厂共性（五条）

1. **开源即自动防御性公开**——公开代码本身就是先有技术（GitHub 时间戳）
2. **许可证必须带专利条款**——Apache 2.0（显式专利授权 + §6 报复条款）优于 MIT（无专利条款）
3. **规范与实现公开，服务与体验留白**——协议给全世界，增值服务自己留
4. **品牌与商标是长期资产**——名字比代码更难重建
5. **保护动作按威胁排序，不按仪式排序**——大厂养法律团队，个人项目只需要零成本护栏

## 二、许可策略（统一 Apache 2.0，不分层）

**决策（2026-09-06）**：全生态所有仓库统一 Apache 2.0，不因"协议消费者/生产者"角色降级。

**为什么不做"消费者项目用 MIT"**：
1. **宽松收益为零**：Apache 2.0 与 MIT 同属 permissive 家族，采用友好度等价（K8s/Swift/Android 官方 SDK 均 Apache 2.0）。降级 MIT 换不来任何采用增量。
2. **防御损失真实**：Apache 2.0 免费附带专利授权（§3）+ 专利报复条款（§6）；MIT 无专利条款，独立创新（UI 范式、驾驶舱交互、认知工艺等）裸奔。
3. **"消费者项目"并不纯粹**：Cellrix 等同时承载协议之外的独立价值（界面范式、认知仪表盘、Helix 特有交互）——协议换采用，实现不换裸奔。

**真正分层的是服务层，不是代码层**（Google/Apple 同构）：
- 代码/协议：全部 Apache 2.0（开放采用 + 欢迎贡献 + 参考实现免费）
- 商业增值服务（托管/企业版）：将来若有，那是服务不是代码，单独闭源——与代码许可策略解耦

**宽松的正确落实**：开放采用、贡献欢迎、参考实现免费、扩展贡献回协议（CI-144 保留区机制）。协议护城河靠**防御性公开**（不是闭源），实现护城河靠 **Apache 专利条款**（不是更严许可），采用率靠**开放**（不是更松许可）。

**文档语言规范（公开呈现）**：README.md 默认英文（面向全世界的公开门面）；
中文版用 `README.zh-CN.md` 副文档，且双向互链。spec/VISION 等关键文档同规则。
内部过程文档（ADR/GROWTH/PLAN 等）不受限，按项目语言习惯书写。

## 三、方法论五条保护原则（哲学裁剪）

1. **按需驱动**：只防真实威胁（专利抢注 > 商标冒用 > 大厂白嫖）。大厂白嫖是开源默认代价，不是威胁——协议的价值就是被采用。
2. **物理事实优先**：GitHub 公开历史 + commit 时间戳 = 最硬的先有技术证据。第三方平台（IP.com 等）只是补充，不是必需。
3. **极致节能**：零成本动作立即做（LICENSE/NOTICE/prior-art/CONTRIBUTING 声明）；高成本动作（正式专利申请、OIN 联盟、法律顾问）挂议程，有真实需要再动。
4. **确定性优先**：保护文件与代码同库同 commit（prior-art as code），不依赖"将来补记"——证据链与代码同步生长。
5. **极致解耦**：保护文档独立于开发流水线（docs/PROTECTION 或 docs/prior-art.md），不污染代码；许可证变更走 ADR 记录，可追溯。

## 五、Prior Art as Code 规范（本方法论标准）

防御性公开必须做到"可验证的公开披露"，弱披露（泛泛而谈）挡不住专利审查员：

1. **同库同 commit**：先有技术文档与实现代码同仓库，commit 时间戳即公开日
2. **可实施（enabling）**：描述足够详细，本领域技术人员可复现（代码路径到文件/函数）
3. **证据路径**：每个创新点标注实现文件 + 首次 commit
4. **可发现**：README 必须链接 prior-art 文档（专利审查员要能找到）
5. **模块化**：单一主文档索引 + 复杂概念独立成篇（可更新、可引用）

FlowModus `docs/prior-art.md` 为本规范的首个参考实现（2026-09-06 公开）。
